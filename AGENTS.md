# Repository Guidelines

## Layout

- `skills/<name>/` holds one skill each: `SKILL.md`, `references/`, and `scripts/`. `sources.json` lists every skill and where it came from (upstream `cursor/plugins` at a pinned revision, or `local customization`).
- The entry scripts of the multi-agent workflows (`pair.sh` in `pstack-pair`, `pstack-pair-guided` and `pstack-trio`, `kitchen.sh` in `pstack-kitchen`) are exec shims into `pstack-pair/scripts/pair.py`. Each skill's `scripts/variant.py` holds its configuration as class attributes (skill, program name, state directory, store label, roles, store directories, slug limit, unfilled pattern, wake dedupe, usage text) and its commands; `pstack_core/variant.py` holds pstack-pair's. The consultant's commands (`discuss` for the trio, `new-consult`, `consult`, `advice`) are Python in `pstack-pair/scripts/pstack_core/consult.py`, which the trio's and the kitchen's `variant.py` register. `pstack-kitchen/scripts/kitchen.py` reads a repo's `.agents/kitchen.toml` as data.
- `pstack-pair/scripts/pair.py` and `pstack_core/` are the stdlib-only Python core; `pstack_core/cli.py` builds the context from the skill's variant class, answers `help`, a missing command and an unknown word, and dispatches; `errors` the exceptions (`Die` and `Exit` for a command that ends itself, `PairError` and its subclasses for a failure a helper reports) and `translate`, which turns either into stderr text and an exit code, `store` the context and the store accessors, `panes` the herdr calls (agent start and prompt as named functions, the `HERDR_ENV` check), `argv` the lexical option reader every command's arguments go through (`Spec`, `read`, `Parsed`; the command keeps its own number and choice checks), `git` the git calls, `steplog` the `steps/<unit>.tsv` rows (`Step`, `StepLog`), `procinfo` the process facts read from `/proc`, `send` the message delivery with `dispatch` and `discuss`, `commands/rotate` `queue`, `failover` and `rotate_if_due`. The variant classes are in `pstack-pair-guided`, `pstack-trio` and `pstack-kitchen`. The contract the tests hold it to is [`tests/SPEC.md`](tests/SPEC.md) (generated by `tests/spec_gen.py`; every line names the test that asserts it) plus the golden transcripts in `tests/pstack-pair/golden`. [`tests/PARITY.md`](tests/PARITY.md) lists the few caller-visible differences from the old bash.
- `pstack-kitchen/scripts/kitchen_core/` holds every command of `kitchen.sh` in Python; The kitchen variant's startup hook stamps the skills build on a store named as the second word. The modules: `step` (step, finish and their detached gate and Verify runs), `wait` (the quiet wait), `dispatch` (dispatch, queue and discuss; the consultant plan round and `rotate_if_due` are pstack_core's, in `consult` and `commands/rotate`), `setup` (init, spawn, consultant, fleet), `classify`, `verify` with `verify_state` and `verify_wait` (the verdict wait and `warn_unreviewed`), `units` and `landing` (land-check, revise), `master`, `handoff`, `feedback`, `ledger` (catch, retro) and `worker` (the detached gate and Verify runner). They run through the kitchen's `variant.py`, which `pstack_core/cli.py` asks for any command name the core lacks and for the few the core lets a variant replace (`OVERRIDABLE`); `kitchen_core/kpy.py` is its only way into `kitchen.py`.
- `scripts/pstack-sync.py` installs the skills as per-skill links for each agent runtime; `scripts/check-pstack.py` checks the inventory, frontmatter and links.
- `tests/` drives the scripts against a fake `herdr` (`tests/pstack-pair/bin`) and compares golden transcripts (`tests/pstack-pair/golden`).

## Style

- The entry scripts stay one exec line and `bash -n` clean; Python is stdlib-only, Python 3.11 or later.
- Skill text: say what holds, in plain sentences; link with relative paths that `check-pstack.py` can resolve.
- Name commits with Conventional Commits and a scope naming the skill or area (`fix(skills/pstack-kitchen): ...`, `test(tests): ...`). Keep commits atomic.

## Testing Guidelines

- `python3 scripts/check-pstack.py` and `python3 tests/run.py` must pass before a commit. `tests/run.py` runs one process per test in parallel; `-k <text>` selects tests by id; `PSTACK_PAIR_UPDATE=1` regenerates the pair goldens, and a golden changes only when the transcript is meant to change.
- Commit a source change in the same commit as the test that pins it; the kitchen's `test-touch` policy refuses a step under `skills/pstack-pair` that changes source with no file under `tests/`.
- Tests are deterministic: no sleeps and no elapsed-time asserts. Trigger a state change at a fixed point with the fake herdr hooks (`$FAKE/once/<subcommand>`, `$FAKE/report-after`) and assert on output.
- Tests are hermetic: they scrub inherited `PSTACK_KITCHEN_*`, `KITCHEN_*` and `PAIR_*` variables, so a run inside a live kitchen gives the same result as one outside it.
- Drive pair.sh and kitchen.sh by hand only against the fake herdr: put `tests/pstack-pair/bin` first on PATH and point XDG_STATE_HOME at a temp directory, as `tests/pstack-pair/scenario.sh` does (it unsets `PSTACK_KITCHEN_ROLE` and `PSTACK_KITCHEN_RUN`, which a verifier pane carries). `init`, `spawn`, `stop` and `close` against the real herdr register, rename or close the calling pane, so an agent that runs them there loses its own pane.

## Security

- No secrets in the repo; agents read tokens from the host environment.
- Host-specific settings (the agent roster in `~/.config/pstack/kitchen.toml`, model preferences in `~/.config/pstack/models/`) stay on the host.
